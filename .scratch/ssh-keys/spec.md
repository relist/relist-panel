# Spec — SSH keys as a host-wide library chosen by each Git Source

Date: 2026-10-25.
Status: needs-triage

## Problem

Each Git Source owns one Deploy key, generated when the Source is first saved
(`compose_sources.ssh_private_key` / `ssh_public_key`, ADR-0016). An operator whose
repositories are reached through one machine-user key, or who wants the same key on
several repositories, cannot reuse a key: every Compose gets a fresh pair that has to be
added to its repository separately. There is also no place that lists every key and
where it is used.

## Goal and success criteria

- A new **SSH keys** menu, host-wide, lists every SSH key with its name, public key,
  creation time and the Composes that use it.
- The operator generates a key there (ed25519, named), copies its public half, renames
  it, and deletes it.
- A Git Source chooses one SSH key from a select box. One key can serve many Composes.
  Whether one key goes on several repositories is the operator's choice on the Git host.
- Keys are generated only on the SSH keys page. The Source modal only selects.
- Existing per-Source keys are discarded. Existing Git Sources have no key after the
  upgrade and show a warning until one is chosen.
- A queued Deployment keeps the key material it was queued with (ADR-0017), so deleting
  a key does not break Deployments already in the queue.

## Out of scope

- Importing an existing private key. Keys are only generated by the panel.
- Regenerating a key in place. To rotate, generate a new key and switch Sources to it.
- Key types other than ed25519, and passphrase-protected keys.
- Per-Project or per-Environment key scopes. The library is host-wide.

## Domain changes

- `CONTEXT.md`: the term **Deploy key** becomes **SSH key**: "An SSH key pair the panel
  generates and keeps in the host-wide SSH keys library. A Git Source chooses one; one
  key may serve many Composes. The operator adds its public half to each repository as a
  read-only deploy key." The `_Avoid_: SSH key` line is removed; avoid "Credential".
  References to "Deploy key" elsewhere in the glossary (Source, Deployment) are updated.
- New `docs/adr/0020-ssh-key-library.md` supersedes ADR-0016's "per-Compose Deploy key the
  panel generates". The reason for one-per-Compose (Git hosts refuse one deploy key on two
  repositories) is now the operator's concern: a machine-user key works across
  repositories, and the panel does not police reuse.

## Data model

New migration `internal/migrations/00021_ssh_keys.sql`. Committed migrations are not edited.

```sql
CREATE TABLE ssh_keys (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    name TEXT NOT NULL UNIQUE,
    private_key TEXT NOT NULL,
    public_key TEXT NOT NULL,
    created_at INTEGER NOT NULL
);
ALTER TABLE compose_sources ADD COLUMN ssh_key_id INTEGER REFERENCES ssh_keys(id) ON DELETE SET NULL;
UPDATE compose_sources SET ssh_private_key = '', ssh_public_key = '', last_test_at = NULL, last_test_ok = NULL;
```

- `ssh_private_key` / `ssh_public_key` are not dropped: no code reads them after this
  change, and dropping them in SQLite would rebuild the table. A comment in the migration
  says they are retired.
- `last_test_*` is cleared because the test it records used the discarded key.
- `foreign_keys(1)` is already set in the DSN (`internal/database/database.go`), so
  `ON DELETE SET NULL` applies.
- The public key's comment is `relist-<name>` at generation time. Renaming does not
  change it; Git hosts ignore the comment.
- Names are trimmed, required, and unique ignoring case (`COLLATE NOCASE`, like `projects.name`).

`sources.Source` keeps its `PrivateKey` and `PublicKey` fields, now filled by joining
`ssh_keys` in `Store.Get`, and gains `SSHKeyID *int64` and `SSHKeyName string`. The Git
runner, the Deployment snapshot and log redaction keep working unchanged, and a snapshot
carries the key material from queue time. `Store.Put` writes `ssh_key_id` and no longer
writes key material.

## API

### `internal/sshkeys` (new package, wired in `server.go`)

| Route | Body | Result |
|-------|------|--------|
| `GET /api/ssh-keys` | — | `200 [{id, name, publicKey, createdAt, usedBy: [{projectId, projectName, environmentId, composeId, composeName}]}]`, ordered by name |
| `POST /api/ssh-keys` | `{name}` | `201` the new key (same shape, `usedBy: []`) |
| `PATCH /api/ssh-keys/{id}` | `{name}` | `200` the key |
| `DELETE /api/ssh-keys/{id}` | — | `204` |

- No response ever contains the private key.
- Empty name: `400`. Duplicate name: `409 "An SSH key with this name already exists"`.
  Unknown id: `404`.
- `DELETE` runs in one transaction: clears `last_test_*` on Sources that use the key, then
  deletes the key, and `ON DELETE SET NULL` detaches those Sources.
- `GenerateKey` moves from `internal/sources/keys.go` to `internal/sshkeys` (with its test).

### `internal/sources`

- `GET .../source` returns `sshKey: {id, name, publicKey} | null` in place of `publicKey`.
- `PUT .../source` (git) accepts optional `sshKeyId`. Omitted or `null` saves the Source
  without a key. An unknown id: `400`. A changed key clears `last_test_*`. Saving no longer
  generates a key.
- `POST .../source/key` (regenerate) is removed, with `keyComment`.
- `POST .../source/test` with no key: `400 "Choose an SSH key first"`.

### `internal/deployments`

- Queuing a `build` Deployment for a Compose whose Git Source has no SSH key: `400 "Choose an
  SSH key for this Source"`, beside the existing no-branch `400`. `skip-build` does not fetch
  and is allowed. A zip Source and a Compose without a Source are unaffected.
- A legacy Deployment resumed without a snapshot whose Git Source now has no key fails at
  the fetch step with the same reason.
- A queued Deployment uses the key in its snapshot, even if the key is deleted later.

## UI (antd 6.5.1)

Before implementing, read Ant Design's `llms.txt` and the pages for the components used
(Table, Select, Modal, Typography copyable, Alert), and follow `docs/GUIDELINES.md`.

### SSH keys page

- Sidebar item **SSH keys** after Images, icon `KeyOutlined`, path `/ssh-keys`
  (`paths.sshKeys`), breadcrumb Overview › SSH keys.
- `web/src/pages/SshKeysPage.tsx` with its display logic in `ssh-keys-view.ts`.
- Table columns: Name, Public key (copyable, truncated), Used by (links to each Compose,
  or "Not used"), Created, actions (Rename, Delete).
- **Generate key** opens a modal with a required Name field. After creation the modal shows
  the public key with copy, and: "Repository → Settings → Deploy keys → Add deploy key,
  leave write access off. To reuse it, add the same key to each repository." A 409 shows
  under the Name field.
- **Rename** is a modal with the Name field and the same 409 handling.
- **Delete** uses `DangerModal`. When the key is in use, the modal lists the Composes and
  says: "These Sources will have no SSH key and can't deploy until you choose another."

### Source modal (Git)

- The "Deploy key" block becomes a **SSH key** `Select` listing every key by name. Below it,
  the chosen key's public half with copy, and the existing "Repository → Settings → Deploy
  keys" hint.
- With no keys: "No SSH keys yet", a link "Create one in SSH keys" that opens the page in a
  new tab, and a reload button for the list, so the modal keeps its draft.
- Choosing a key persists the Source at once, as the URL does on blur, so Test connection
  uses it.
- Test connection is enabled only when the URL is saved and a key is chosen.
- The Regenerate key button is removed.
- If the chosen key disappears (deleted elsewhere), the modal reloads the key list and
  shows no selection.

### Source card / Compose page

- A Git Source without a key shows a warning `Alert`: "No SSH key — choose one before
  deploying."
