# Docker execution, networking, and storage architecture

The panel needs to drive Docker Compose on the host it runs on, and get Traefik routing to work out of the box for whatever the user deploys.

- The panel shells out to the `docker compose` CLI plugin (installed in the panel's own image) over the host's Docker socket, mounted at `/var/run/docker.sock`, rather than reimplementing compose orchestration against a Go client library — the CLI is the reference implementation of the compose spec, so this gets full fidelity without depending on `docker/compose`'s internal, non-public Go packages.
- Traefik ships bundled in the same install `docker-compose.yml` as the panel itself, along with a shared external network (e.g. `relist-public`). The panel auto-injects that network into every service of a user's pasted Compose file before running it — the one place the panel manages something beyond raw passthrough, because otherwise every user hits the same "why doesn't routing work" gotcha on their first deploy.
- The panel's data directory is bind-mounted at an **identical path** on the host and inside the panel container (default `/var/lib/relist-panel`, configurable via `RELIST_DATA_DIR`) — not a named Docker volume — because `docker compose up` executes against the host's dockerd, so relative paths (build context, bind volumes) in a user's Compose file only resolve correctly if that path exists at the same location on the host as inside the panel container. Each Compose's files live under `<data dir>/<project>/<environment>/<compose>/`. The panel's own SQLite database lives alongside it, at `<data dir>/panel.db`.
- Every Compose deploys under a deterministic Compose project name, `<project-slug>-<environment-slug>-<compose-slug>`, passed via `docker compose -p`, so multiple Composes never collide on container/network names.
