# A Compose that could take the host deploys only once an approver approves it

ADR-0031 gave Editors the Compose file. With nothing else in the way, an Editor could deploy a Compose that mounts the Docker socket or `/`, runs privileged, or opens another Project's volume, then use the Terminal: Editor meant root on the host.

**Decision:** Every Deployment's config is checked against the **Compose policy** before it queues, again after its Source is fetched and before the first build, and again just before `up`. The check reads the paths that deploy (this Deployment's own Source copy), while the hash reads them as the Compose directory's so it is the same from one Deployment to the next. It reads `docker compose config --format json --no-env-resolution` with every profile enabled (`--profile '*'`), on the exact snapshot the Deployment freezes (ADR-0017), so interpolation, `include`, `extends` and profiles cannot hide a value; `include` and `extends` paths are checked in the saved YAML too, since `config` merges them away. The rules are an **allowlist**: a service key the checker does not know is a violation. A config that violates deploys only when `compose_approvals` (migration `00034`) holds an **Approval** for its hash, the SHA-256 of the resolved config with its keys in a fixed order. An approver approves on the Compose page, or by deploying with the hash they were shown; a stale hash answers 409, so an edit saved between looking and clicking is never approved unseen. The hash covers the resolved config and the Compose's Source settings (kind, repository, branch, paths, zip upload), so any change to the config, a variable value included, another repository or a new zip needs a new approval. A new commit on the same branch does not: approving a privileged build of a git Source trusts whoever can push to that branch.

The approver is every Admin (`RELIST_POLICY_APPROVER=admins`, the default) or only the Owner (`owner`). Host paths outside a Compose's directory that it may bind without approval are listed in `RELIST_POLICY_BIND_ROOTS`. Both are read from the environment only, so a stolen Admin session cannot widen them; a bad value stops the panel at startup.

What is refused (internal/policy): a bind, `env_file`, `label_file`, config or secret file outside the Compose directory and the bind roots, after symlinks, any link the panel cannot follow (its target missing from the panel's view) included; the Compose directory itself and its `.ssh` (a Source's git key); a bind of the panel's own files there (any name with a leading dot, `docker-compose.yml`, `sets`) other than this Deployment's own Source copy, since a container that could write one could change what the next Deployment runs; a bind inside another bind; secrets and configs read from the panel's environment; named volumes with `driver_opts`, another driver, `external`, or a name other than `<project>_<key>`; `volumes_from`, `pid`, `ipc`, `uts` or `cgroup` reaching the host or a container outside the Compose; a `network_mode` other than `none` or a service of this Compose (dockerd joins any network named there, another Compose's private one included); `privileged`, `cap_add`, `devices`, `device_cgroup_rules`, `security_opt`, `sysctls`, `cgroup_parent`, `runtime`, `gpus`, `use_api_socket`, `provider`, `userns_mode: host`, privileged hooks, mounts other than bind, volume and tmpfs; build contexts, Dockerfiles and additional contexts outside the Compose directory, host build network, privileged builds, entitlements, build SSH and local build caches, and build or deploy keys it does not know; device reservations under `deploy`; networks other than this Compose's own bridges and the panel's shared network; a `traefik.*` label (in any case) that is not exactly one the panel writes for this Compose's own Domains (`domains.Generated`) with the value it writes, other than `traefik.enable` set false and `traefik.docker.network: relist-network`, since Traefik merges routers, services, middlewares and transports of the same name across every container it reads; a `traefik.*` or `com.docker.*` label under `build.labels`, which lands on the image and from it on the container; an image a service builds (its `image` or `build.tags`) not named `<project>-…`, since the image store is the host's and no Deployment pulls; a `com.docker.*` label on a service, volume or network, which would make it pass as another Compose's, since the panel finds a Compose's containers and volumes by `com.docker.compose.project`. Violation messages and evaluation errors have the Compose's secret values masked, since Viewers read them.

Images are checked at deploy time too (`composes.prepareImages`): the deploy step builds every built Service, pulls the images that are missing (and refreshes those whose `pull_policy` asks for it), and refuses an image that brings its own `traefik.*` labels onto a container Traefik reads (`policy.ImageLabels`). Every `up` and `scale` after it, rollouts included, runs with `--no-build` and `--pull never`, so the images checked are the images that start. This check fails whatever the approval: an approval covers the config, never what an image carries. Setting the key in the Compose's labels, or `traefik.enable: "false"`, overrides the image.

The Volume Explorer checks the deployed file it resolves from: a Volume a violation names opens only for an approver once the current config is approved.

## Security review (2026-11-05)

A security review of the stack against `main` found three ways an Editor could get past the first version of the rules with no approval. All three are now violations (`internal/policy/policy.go`, tests in `check_test.go`):

1. **Traefik labels took the panel's domain.** Only labels naming the panel's host were refused. A router with ``rule=HostRegexp(`.+`)`` or ``PathPrefix(`/`)``, `priority=999999999` (the panel's routers use 100000) and `tls=true` would have been sent every request for the panel, under the panel's own certificate, along with admins' session cookies, passwords and TOTP codes: panel takeover. A plain `Host()` of another Project's Domain would have taken that Project's traffic. Now an HTTP router may only match exactly the rule of one of the Compose's own Domains (`domains.Rule`, the rule the panel writes), may not set a priority, and TCP and UDP routers are refused. Router keys are matched in any case, as Traefik reads them.
2. **A built image could replace another Project's.** `image` and `build.tags` were unchecked. A service building `image: postgres:16` would have tagged the host's `postgres:16`; since no Deployment pulls (`up` with Compose's default `pull_policy: missing`), another Project's next Deployment would have started its database from that image, with its secrets and volumes. Now the names a service builds must start with `<project>-` (`relist-c<ID>-`), Compose's own default; a pulled image may still have any name.
3. **`network_mode` joined another Compose's network.** Only `host`, `container:` and a `service:` outside the Compose were refused, and the `networks` rules never see `network_mode`. `network_mode: relist-c2_default` would have joined Compose 2's private network and reached its databases. Now only `none` and `service:<a service of this Compose>` pass; `bridge` needs approval too, since the default bridge is shared with every other container on it.

A Compose that hand-writes routers for its own Domains with a different rule, sets a priority, or builds an image under another name now needs approval once.

**Round 2.** A second review of the fixed stack found two more ways to take the panel's traffic:

4. **Labels from the image.** The checks read only the Compose's `labels`. Docker merges an image's `LABEL`s into its containers' labels, and Traefik reads them, so a Dockerfile in the Compose's Source (or `build.labels`, or a pulled image) with `traefik.enable=true` and a router for the panel's host at priority 200000 passed with no violation. Now `build.labels` follow the label rules, and the deploy step builds and pulls every image, refuses one whose own Traefik labels would reach Traefik, and starts only those images (no rebuild, no second pull, since a registry could answer it with another image).
5. **Traefik service merging.** Only router labels were checked. Traefik merges same-named services from different containers into one load balancer, so `traefik.http.services.panel.loadbalancer.server.port=80` added the Editor's container as a second server of the panel's own `panel` service and drew half of the panel's requests; a Domain's `relist-c<ID>-d<ID>` service could be joined the same way. Middlewares and transports share that namespace too. Patching key family after key family had already missed this twice, so the first round's ruling is revised: a Compose may carry only the Traefik labels the panel writes for its own Domains, with their exact values. Anything hand-written needs approval.

## Only an admin writes the file (2026-11-05)

Three review rounds kept finding new ways a Compose file reaches past the rules: Compose exposes nearly the whole Docker API, and Traefik merges labels across every container on one shared host. Checking an Editor's file key by key does not converge. So **only an Admin creates a Compose, saves its YAML, or previews an unsaved file** (`POST …/composes`, `PUT …/composes/{id}`, `POST …/preview` are admin-only routes). An Editor still deploys it and changes its Variables, Variable Sets, Domains, Source, Builder and zero-downtime switches, and opens the Terminal and the Volume Explorer.

The policy and the image check stay, because an Editor still shapes what deploys in two ways: a Variable interpolated into the file (`image: ${IMAGE}`, a label value), and a Source whose Dockerfile builds the image. The image check now reads the labels of the platform each Service runs (`docker image inspect --platform`): one tag can hold a different image per platform, so reading the host's would check an image that never starts.

A host belongs to one Project. A Domain was unique only on host and path, so an Editor could claim a longer path (`shop.com/login`) or a shorter one (`shop.com/`) on a host another Project serves, and Traefik, which prefers the longer rule, sent that Project's requests to them under a certificate for its host. Creating or moving a Domain onto a host a Compose of another Project serves now answers 409, for Admins too, without naming the other Project. Composes of one Project still share a host by path. Domains already shared across Projects before this rule are left as they are; only new or changed ones are refused.

## Considered options

**Checking the YAML before the panel injects its keys.** The spec's wording. Rejected for what deploys: the snapshot is what `up` runs, and the panel's own keys (Domain labels, the shared network, the log cap, Variable Set files) pass the rules.

**Refusing every hand-written Traefik label.** First rejected because only the rule and priority seemed to decide which requests a router takes. Round 2 showed that wrong (services merge by name across containers), so it is now the rule: only the labels the panel writes for the Compose's Domains pass without approval.

**A form for Editors instead of a file** (image, port, environment, named volumes, resources, healthcheck, Domains), the way ECS or Cloud Run take a service. Deferred, not rejected: the panel would write every key itself, so the surface is the form's fields, not Compose's. It is a feature of its own and needs its own spec.

**Creating the containers, inspecting them, then starting them.** Rejected for image labels: it relies on Traefik ignoring created containers, and on a violation it has already replaced the running ones. Checking the images first fails before anything running is touched.

**Pulling every image that is not built before `up`.** Rejected for the fix: it changes every Deployment (registry rate limits, offline hosts), and a tag pushed to a local registry would still be shared. Namespacing what a Compose builds stops it at the source.

**A denylist.** Rejected: Compose grows keys (`use_api_socket`, `provider`) faster than a denylist would follow.

**Showing the hash to everyone.** Rejected: it is a hash over interpolated secret values, which a Viewer could test guesses against. Only approvers get it.

## Consequences

- **Admins remain fully trusted.** An Admin who is not an approver still uses the host-wide pages (Docker host, Migration serve hands out `panel.db`).
- **Composes already running are untouched**; their next deploy is checked. Restart and stop are not checked.
- **What it does not stop:** a kernel exploit from an ordinary container; a symlink race across Deployments (a container from the previous Deployment that can write a bound directory could swap a path between the check and `up`; the nesting rule closes it within one config and the last check runs just before `up`); symlinks under a bind root the panel container cannot see, which are compared as text; an `include` or `extends` deeper than eight files.
- A git Source in build mode cannot be resolved before it is fetched; such a Deployment queues and the check after the fetch decides.
- The Compose list shows no policy tag: an accurate one would run `docker compose config` per Compose per load.
