# A Compose that could take the host deploys only once an approver approves it

ADR-0031 gave Editors the Compose file. With nothing else in the way, an Editor could deploy a Compose that mounts the Docker socket or `/`, runs privileged, or opens another Project's volume, then use the Terminal: Editor meant root on the host.

**Decision:** Every Deployment's config is checked against the **Compose policy** before it queues, again after its Source is fetched and before the first build, and again just before `up`. The check reads the paths that deploy (this Deployment's own Source copy), while the hash reads them as the Compose directory's so it is the same from one Deployment to the next. It reads `docker compose config --format json --no-env-resolution` with every profile enabled (`--profile '*'`), on the exact snapshot the Deployment freezes (ADR-0017), so interpolation, `include`, `extends` and profiles cannot hide a value; `include` and `extends` paths are checked in the saved YAML too, since `config` merges them away. The rules are an **allowlist**: a service key the checker does not know is a violation. A config that violates deploys only when `compose_approvals` (migration `00034`) holds an **Approval** for its hash, the SHA-256 of the resolved config with its keys in a fixed order. An approver approves on the Compose page, or by deploying with the hash they were shown; a stale hash answers 409, so an edit saved between looking and clicking is never approved unseen. The hash covers the resolved config and the Compose's Source settings (kind, repository, branch, paths, zip upload), so any change to the config, a variable value included, another repository or a new zip needs a new approval. A new commit on the same branch does not: approving a privileged build of a git Source trusts whoever can push to that branch.

The approver is every Admin (`RELIST_POLICY_APPROVER=admins`, the default) or only the Owner (`owner`). Host paths outside a Compose's directory that it may bind without approval are listed in `RELIST_POLICY_BIND_ROOTS`. Both are read from the environment only, so a stolen Admin session cannot widen them; a bad value stops the panel at startup.

What is refused (internal/policy): a bind, `env_file`, `label_file`, config or secret file outside the Compose directory and the bind roots, after symlinks, any link the panel cannot follow (its target missing from the panel's view) included; the Compose directory itself and its `.ssh` (a Source's git key); a bind of the panel's own files there (any name with a leading dot, `docker-compose.yml`, `sets`) other than this Deployment's own Source copy, since a container that could write one could change what the next Deployment runs; a bind inside another bind; secrets and configs read from the panel's environment; named volumes with `driver_opts`, another driver, `external`, or a name other than `<project>_<key>`; `volumes_from`, `pid`, `ipc`, `uts` or `cgroup` reaching the host or a container outside the Compose; a `network_mode` other than `none` or a service of this Compose (dockerd joins any network named there, another Compose's private one included); `privileged`, `cap_add`, `devices`, `device_cgroup_rules`, `security_opt`, `sysctls`, `cgroup_parent`, `runtime`, `gpus`, `use_api_socket`, `provider`, `userns_mode: host`, privileged hooks, mounts other than bind, volume and tmpfs; build contexts, Dockerfiles and additional contexts outside the Compose directory, host build network, privileged builds, entitlements, build SSH and local build caches, and build or deploy keys it does not know; device reservations under `deploy`; networks other than this Compose's own bridges and the panel's shared network; a `traefik.*` label naming the panel's own domain (only Traefik reads labels, so others may); an HTTP router whose `rule` is not exactly the rule of one of this Compose's own Domains, any router `priority`, and any TCP or UDP router, since Traefik routes by rule and priority across every Compose; an image a service builds (its `image` or `build.tags`) not named `<project>-…`, since the image store is the host's and no Deployment pulls; a `com.docker.*` label on a service, volume or network, which would make it pass as another Compose's, since the panel finds a Compose's containers and volumes by `com.docker.compose.project`. Violation messages and evaluation errors have the Compose's secret values masked, since Viewers read them.

The Volume Explorer checks the deployed file it resolves from: a Volume a violation names opens only for an approver once the current config is approved.

## Security review (2026-11-05)

A security review of the stack against `main` found three ways an Editor could get past the first version of the rules with no approval. All three are now violations (`internal/policy/policy.go`, tests in `check_test.go`):

1. **Traefik labels took the panel's domain.** Only labels naming the panel's host were refused. A router with ``rule=HostRegexp(`.+`)`` or ``PathPrefix(`/`)``, `priority=999999999` (the panel's routers use 100000) and `tls=true` would have been sent every request for the panel, under the panel's own certificate, along with admins' session cookies, passwords and TOTP codes: panel takeover. A plain `Host()` of another Project's Domain would have taken that Project's traffic. Now an HTTP router may only match exactly the rule of one of the Compose's own Domains (`domains.Rule`, the rule the panel writes), may not set a priority, and TCP and UDP routers are refused. Router keys are matched in any case, as Traefik reads them.
2. **A built image could replace another Project's.** `image` and `build.tags` were unchecked. A service building `image: postgres:16` would have tagged the host's `postgres:16`; since no Deployment pulls (`up` with Compose's default `pull_policy: missing`), another Project's next Deployment would have started its database from that image, with its secrets and volumes. Now the names a service builds must start with `<project>-` (`relist-c<ID>-`), Compose's own default; a pulled image may still have any name.
3. **`network_mode` joined another Compose's network.** Only `host`, `container:` and a `service:` outside the Compose were refused, and the `networks` rules never see `network_mode`. `network_mode: relist-c2_default` would have joined Compose 2's private network and reached its databases. Now only `none` and `service:<a service of this Compose>` pass; `bridge` needs approval too, since the default bridge is shared with every other container on it.

A Compose that hand-writes routers for its own Domains with a different rule, sets a priority, or builds an image under another name now needs approval once.

## Considered options

**Checking the YAML before the panel injects its keys.** The spec's wording. Rejected for what deploys: the snapshot is what `up` runs, and the panel's own keys (Domain labels, the shared network, the log cap, Variable Set files) pass the rules.

**Refusing every hand-written Traefik label.** Rejected: a router for the Compose's own Domain with its own middlewares is a common shape and reaches nothing; only the rule and priority decide which requests it takes.

**Pulling every image that is not built before `up`.** Rejected for the fix: it changes every Deployment (registry rate limits, offline hosts), and a tag pushed to a local registry would still be shared. Namespacing what a Compose builds stops it at the source.

**A denylist.** Rejected: Compose grows keys (`use_api_socket`, `provider`) faster than a denylist would follow.

**Showing the hash to everyone.** Rejected: it is a hash over interpolated secret values, which a Viewer could test guesses against. Only approvers get it.

## Consequences

- **Admins remain fully trusted.** An Admin who is not an approver still uses the host-wide pages (Docker host, Migration serve hands out `panel.db`).
- **Composes already running are untouched**; their next deploy is checked. Restart and stop are not checked.
- **What it does not stop:** a kernel exploit from an ordinary container; a symlink race across Deployments (a container from the previous Deployment that can write a bound directory could swap a path between the check and `up`; the nesting rule closes it within one config and the last check runs just before `up`); symlinks under a bind root the panel container cannot see, which are compared as text; an `include` or `extends` deeper than eight files.
- A git Source in build mode cannot be resolved before it is fetched; such a Deployment queues and the check after the fetch decides.
- The Compose list shows no policy tag: an accurate one would run `docker compose config` per Compose per load.
